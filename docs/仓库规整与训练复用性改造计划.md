# Aar_Unilab 仓库规整与训练复用性改造计划（讨论稿）

> 状态：目标讨论稿，尚未进入代码迁移阶段
> 日期：2026-09-15
> 目标仓库：`/ssd/Pheonix/Aar_Unilab`
> 当前核心对象：WE11 轮足机器人 RSL-RL PPO + MuJoCo 训练、回放、C++ Sim2Sim 与策略交付

## 1. 文档目的

本文用于讨论并确认 Pheonix 工作区的仓库规整目标、保护边界、目标结构、迁移顺序和验收标准。

本次改造不是重新设计当前 WE11 轮足训练任务，也不是用历史代码覆盖现有成果。改造的首要任务是完整保留当前已经调试优化过的训练环境、配置、资产、控制语义和 checkpoint 合同；在此基础上，把训练、Python 回放和 C++ Sim2Sim 整理进一个可以独立完整 clone 的仓库，并逐步恢复对其他样机的扩展能力。

本文确认前，不进行目录删除、Git 历史改写、训练参数调整或大规模代码移动。

## 2. 背景与当前问题

当前 `/ssd/Pheonix` 是一个工作区集合，而不是单一 Git 仓库，主要包含：

- `UniLab/`：当前 WE11 训练代码、配置、资产、测试、日志和 checkpoint；
- `Play/`：独立的 C++ MuJoCo/ONNX 回放与策略发布闭环；
- `DeployHostDevice/Deploy/`：设备侧部署工作区；
- `DeployHostOnly/`、`DeployHistory/`：部署副本和历史归档；
- `artifacts/`、`temp/`、`temp-repo/`：策略、运行数据和临时副本。

当前存在以下问题：

1. `UniLab/.git` 和 `Play/.git` 是指向 `/ssd/dog/sar_unilab/.git/worktrees/` 的 worktree 指针，单独复制目录不能得到完整独立仓库。
2. UniLab、Play 和 Deploy 以内容差异很大的分支或仓库维护，不能通过一次普通 checkout 同时获得完整训练和回放工作区。
3. 训练端与 C++ Play 重复维护机器人资产、观测顺序、动作维度、控制频率、Kp/Kd、action scale 和 command delay 等策略合同。
4. 训练环境改变时，Play 侧需要手工同步，存在静默漂移风险。
5. 当前仓库是 WE11 专用归档，公共框架代码中仍有较多 WE11/DR002 专用逻辑，不便接入其他样机。
6. 日志、虚拟环境、构建产物、历史快照和源码混放，增加了理解、备份和迁移成本。
7. 当前有效工作区包含未提交和未跟踪成果，仅从远端重新 clone 不能完整恢复当前训练状态。
8. 当前 Conda 根目录为 `/data/miniconda3`，已占用约 63 GB；默认 `envs_dirs` 和 `pkgs_dirs` 落在 `/data/miniconda3` 或空间紧张的 `/home/angela/.conda`。现有安装脚本只接受环境名，不能保证 Conda 本体、环境和缓存全部落在 `/ssd`。
9. 当前 Python 导出入口和 C++ Play 存在 WE11 task name、145 维 observation、6 维 action 等硬编码，不利于新样机接入。
10. editable install、native extension 和部分 CMake 构建结果可能记录仓库绝对路径，仓库移动后需要显式重绑定和验证。

## 3. 总体目标

### 3.1 第一目标：保护当前 WE11 训练成果

新仓库必须以当前 `pheonix-we11/unilab-bringup` 本地有效状态为训练基线，包括：

- 当前本地领先远端的提交；
- 当前确认有效的未提交修改；
- 当前确认属于项目成果的未跟踪文件；
- 最新 Flat、Rough、Getup 任务配置；
- 最新轮足模型、控制参数、奖励、课程、reset、domain randomization 和观测合同；
- 与当前训练环境对应的 checkpoint、ONNX 和来源信息。

历史提交 `652356ac` 及裁剪前代码只作为通用架构和历史功能参考，不作为新仓库的训练行为基线。

### 3.2 第二目标：Train 与 Python Play 同仓同源

训练与日常回放采用同一个 Python 仓库，在同一目录提供清晰入口：

```text
scripts/
├── train.py
├── play.py
├── train_rsl_rl.py          # WE11 迁移期兼容入口
├── export_policy.py
└── visualize_task_env.py
```

`train.py` 和 `play.py` 是稳定的多算法前门，根据选中的 AlgorithmSpec/PolicySpec 路由到对应 adapter；`train_rsl_rl.py` 在第一阶段保留为 WE11 命令兼容入口。对于同一组 robot/task/observation/policy/algorithm 配置，Train 与 Python Play 必须复用：

- 同一个 Hydra task 配置；
- 同一个环境类；
- 同一个 MuJoCo backend；
- 同一套机器人资产；
- 同一个 observation/action 构造实现；
- 同一套 checkpoint 加载和策略网络合同。

Python Play 不另建一份训练环境，不复制一份 WE11 YAML，也不重新实现 observation/action。

### 3.3 第三目标：保留同仓的 C++ Sim2Sim

当前 C++ Play 保留其跨语言、跨推理运行时和部署前验证价值，但不再作为一套独立、手工同步的完整训练环境维护。它将迁入 `Aar_Unilab/sim2sim/`，明确定位为数据驱动的 C++ Sim2Sim：

- 使用 C++、MuJoCo 和 ONNX Runtime 执行导出策略；
- 验证 observation/history/action/control/delay 等部署合同；
- 保留必要的实时窗口、键盘/手柄和场景回放能力；
- 只消费训练端生成的 release bundle；
- 不独立维护机器人资产、策略维度、Kp/Kd、action scale 和控制频率；
- 不复刻训练 reward、完整 curriculum 或完整 domain randomization。

Python Play 是日常训练回放入口；C++ Sim2Sim 是部署前的一致性验证入口。两者保留不同职责，但位于同一个仓库和同一个 Git commit 下。

### 3.4 第四目标：仓库可独立完整 clone

最终仓库使用普通 `.git/` 目录，不依赖其他路径中的 Git common directory 或 worktree 元数据。

目标仓库名称固定为 `Aar_Unilab`，第一阶段存放地址固定为：

```text
/ssd/Pheonix/Aar_Unilab
```

该位置只是为了便于在当前 VS Code 工作区中查看，不代表它可以依赖父目录。`Aar_Unilab` 必须是完全独立的普通 Git 仓库；运行、构建、测试和回放不得读取 `../UniLab`、`../Play`、`../DeployHostOnly`、`../DeployHostDevice`、`/ssd/dog/sar_unilab` 或其他父级/相邻工作区内容。

在一台干净机器上执行一次普通 clone 后，应能够获得训练、Python Play 和 C++ Sim2Sim 所需的全部源码、配置和必要资产，并能按照文档完成安装、冒烟训练、checkpoint 回放和 Sim2Sim 合同测试。

### 3.5 第五目标：逐步提升多样机复用性

在 WE11 行为被基线测试保护后，逐步分离：

- 机器人本体合同；
- 任务合同；
- observation/critic observation 合同；
- policy/network 合同；
- 算法配置；
- 仿真后端；
- 策略导出与运行时合同。

目标调用形式：

```bash
python scripts/train.py robot=we11 task=joystick_flat algorithm=rsl_rl_ppo policy=we11_adapt simulator=mujoco
python scripts/play.py  robot=we11 task=joystick_flat algorithm=rsl_rl_ppo policy=we11_adapt simulator=mujoco

python scripts/train.py robot=pe01 task=locomotion_flat algorithm=<pe01_algorithm> policy=<pe01_policy> simulator=mujoco
```

新增另一台样机时，应以增加 robot/task/observation/policy/algorithm profile 和必要扩展为主，避免复制完整框架或修改公共训练入口。新样机不要求复用 WE11 的算法、观测、网络和奖励，只要求遵守公共环境与训练运行协议。

### 3.6 第六目标：环境安装在 SSD，仓库路径可迁移

为避免继续占用容量不足的磁盘，`Aar_Unilab` 不沿用 `/data/miniconda3` 作为运行环境的 Conda base。计划在 `/ssd` 安装一套独立 Miniforge/Conda，使 Conda 程序本体、base、environment、package cache、pip cache 和 native build cache 全部位于 `/ssd`。

推荐本机默认布局：

```text
/ssd/conda/miniforge3/             # 独立 Conda/Miniforge 本体和 base
/ssd/conda/envs/aar_unilab/        # Aar_Unilab environment prefix
/ssd/conda/pkgs/                   # Conda package cache
/ssd/conda/cache/pip/              # pip cache
/ssd/conda/cache/aar_unilab-native/ # native extension build cache
```

安装脚本必须支持显式 `--conda-base` 和 `--prefix`，不得调用 PATH 中不确定来源的 Conda，也不得只支持 Conda 环境名。上述路径是本机推荐默认值，但可通过参数覆盖，以保证其他机器可安装。

旧 `/data/miniconda3` 在 `Aar_Unilab` 的 SSD 环境完成全部验收前保持不动。后续是否清理旧 Conda 属于单独的磁盘治理任务，不纳入本次仓库迁移的自动步骤。

仓库开发期位于 `/ssd/Pheonix/Aar_Unilab`，最终将移动到：

```text
/ssd/Aar_Unilab
```

源码、配置、manifest 和 CMake 不得写死任一仓库绝对路径。仓库移动后应通过统一的重绑定命令重新执行 editable install 和 native extension 构建，然后完成全套验证。

## 4. 明确不做的事情

第一阶段不包含以下工作：

- 不回退当前 WE11 训练参数；
- 不以历史通用仓库覆盖当前 UniLab；
- 不为了目录美观重写已经验证的环境逻辑；
- 不修改 reward 数值、课程比例、reset 分布或 termination 条件；
- 不修改 observation 顺序、历史长度、action 顺序或策略网络维度；
- 不修改 400 Hz physics、200 Hz motor control、50 Hz policy 等时序合同；
- 不修改当前 command delay 语义；
- 不立即恢复全部旧机器人、旧算法或 Motrix 后端；
- 不在尚未建立基线前删除当前 Play、历史快照或训练数据；
- 不把真机 CAN/ROS2 控制逻辑并入 Python 训练进程。
- 不让新仓库通过相对路径、软链接或环境变量回退到父目录获取源码、配置、模型、资产或运行库；
- 不删除 C++ Sim2Sim 的跨语言验证能力，只减少其重复配置和重复资产。
- 不把 Conda environment 或下载/build cache 放在 Git 仓库内部；
- 不假设仓库永远位于 `/ssd/Pheonix/Aar_Unilab`；
- 不在公共训练、导出、Play 或 Sim2Sim 代码中写死 `we11`、`WE11`、145 维或 6 维等样机专用常量。

基线测试的目的不是要求浮点仿真在所有机器上逐 bit 相同，而是及时发现配置、维度、时序和显著行为漂移。

## 7. Python Play 设计

### 7.1 入口设计

建议建立两个通用薄入口，由 registry 选择内部应用 adapter：

```text
scripts/train.py
scripts/play.py
        │
        └── src/unilab/training/registry.py
            ├── rsl_rl_app.py
            └── <future_algorithm>_app.py

每个 app adapter 提供一致的生命周期接口：

            ├── compose_config()
            ├── create_environment()
            ├── create_runner()
            ├── load_checkpoint()
            ├── run_training()
            └── run_playback()
```

当前 `unilab.cli:eval_main` 已通过调用 `train_rsl_rl.py` 并设置 `training.play_only=true` 实现 WE11/RSL-RL 基础回放路由。新通用 Play 首先把该路径接入 RSL-RL adapter，而不是从零重写环境；后续算法通过各自 adapter 接入，不强迫复用 RSL-RL runner。

Python Play 与 C++ Sim2Sim 的第一版交互能力均应覆盖：

- 可用的实时页面/窗口渲染；
- 在 MuJoCo 视图中通过拖动对机器人施加外力；
- 手柄控制 command 和必要的模式切换；
- 关键状态、command、action、torque 等图表绘制；
- 可旋转、缩放、平移、跟随和切换关注对象的摄像机；
- 对关键输入和控制状态的可视化/日志诊断。

当前 C++ Play 的交互实现虽然并不完整，但作为功能迁移和交互习惯参考；迁移时先建立能力对照表，再决定复用、重写或统一实现的位置。

### 7.2 Play 允许覆盖的内容

Play 可以覆盖运行性质参数，例如：

- `training.play_only=true`；
- 交互或录制 render mode；
- `algo.num_envs=1`；
- checkpoint/run 选择；
- 摄像机、窗口、键盘或手柄输入；
- 是否暂停、回放速度和调试显示。

Play 不得单独覆盖训练合同参数，例如：

- reward 和 curriculum；
- observation/action 定义；
- Kp/Kd 和 action scale；
- command delay；
- robot asset；
- timestep/decimation；
- reset 和 termination。

如确有“回放专用覆盖”，必须显式标注为 visualization/runtime override，并证明不会改变输入给 policy 的合同。

### 7.3 C++ Play 向 Sim2Sim 的改造

当前 C++ Play 的核心能力保留，但从独立工作区迁入新仓库的 `sim2sim/`，并改造为小型、通用、数据驱动的部署前验证程序。

保留：

- ONNX Runtime 推理；
- MuJoCo 实时运行；
- observation/history 构造；
- action scale、clip、PD 和 command delay；
- 键盘和手柄；
- Flat/Rough/Getup 场景；
- 必要的初始状态、wrench/wing-angle 回放；
- observation、raw action、scaled action、torque 和状态 trace。

迁出或删除重复职责：

- C++ Play 自己维护的训练配置；
- C++ Play 自己复制的 WE11 MJCF 和数据资产；
- 手工写死的 `145 -> 6`、关节顺序和控制参数；
- reward、完整训练 curriculum 和完整 domain randomization 复刻；
- 与 Sim2Sim 无关的历史 RL SDK 分支和发布逻辑；
- 已纳入依赖安装/锁定流程的预编译库副本。

C++ Sim2Sim 的标准调用目标为：

```bash
sim2sim --bundle releases/we11/<run-id>
```

它只读取 bundle 中的 manifest、ONNX、运行时配置和必要资产；不允许从父目录或旧 `Play/` 查找缺失内容。

### 7.4 Python 与 C++ 的三层一致性测试

第一层为静态合同测试：

- ONNX 输入输出维度；
- joint/action 顺序；
- observation term 与 history 总维度；
- Kp/Kd、scale、clip 和 limit 数组长度；
- physics/motor/policy 频率及整除关系；
- manifest schema/version；
- bundle 文件 SHA-256。

第二层为单步数值测试：训练端生成固定的原始状态、observation、PyTorch action 和中间控制量；C++ 使用相同输入验证 observation 拼装与 ONNX action。重点比较：

```text
raw state -> observation -> history -> raw action -> scaled action -> target/torque
```

第三层为短轨迹 Sim2Sim 测试：两侧使用相同 MJCF、初始 `qpos/qvel`、command、随机种子、delay 和策略，分别比较 1 个 physics step、1/10/100 个 policy step。长轨迹允许配置合理容差，但必须能够定位首次出现差异的层级。

### 7.5 运行时版本一致性

当前 Python 训练环境实际使用 `mujoco-uni/mujoco 3.8.0`，C++ Play 打包的是 MuJoCo 3.2.7。为保护当前 WE11 训练物理行为，新仓库统一以 **MuJoCo 3.8.0** 为目标基线，C++ Sim2Sim 升级并对齐 3.8.0，而不是让 Python 训练环境降级到 3.2.7。

迁移过程中保留 C++ 3.2.7 的回放结果作为 legacy 对照，记录升级到 3.8.0 后的 XML 加载、接触、控制和短轨迹差异。只有 Python 3.8.0 baseline 与新 C++ 3.8.0 三层合同测试通过后，才移除 C++ 3.2.7 runtime。

C++ 依赖应通过可复现的安装脚本和锁文件管理，至少记录版本、来源和 SHA-256。需要离线部署时可以另存离线依赖包，但源码不得依赖父目录中的 runtime。

## 8. 策略导出与单一数据源

训练配置和机器人 profile 应是策略合同的唯一源头。C++ Sim2Sim 和 Deploy 都是合同消费者，不拥有可独立修改的同名参数。

C++ Sim2Sim 不依赖训练算法实现。无论策略来自 RSL-RL PPO、PE01 前身的自定义 PPO + encoder，还是后续其他算法，只要导出器将推理所需的预处理、history/state、网络输入输出和控制后处理完整固化到 policy contract/bundle，C++ 就按 manifest 执行。reward、optimizer、rollout storage 和训练期 critic 不进入部署运行时；若 actor 包含 encoder、RNN hidden state 或多输入，则由 PolicySpec 明确导出签名，不能强行压成 WE11 当前的单一 145D 输入。

推荐数据流：

```text
训练配置 + Robot Profile
          │
          ├── Python Train
          ├── Python Play
          └── Policy Export
                    │
                    └── Release Bundle
                        ├── policy.onnx
                        ├── deployment_manifest.json
                        ├── runtime_config.yaml
                        ├── 必要机器人资产/scene
                        ├── golden_inputs
                        ├── golden_outputs
                        └── SHA256SUMS
```

部署侧只能消费生成的 manifest/bundle，不再手写一套与训练端平行的策略参数。

训练时的 domain-randomized 参数与部署时的 nominal 参数需要明确区分，但二者应由同一个 robot profile 定义和校验。

manifest 至少包含两类版本：

```json
{
  "manifest_schema_version": 1,
  "policy_contract_version": "we11-v3"
}
```

C++ 对不支持的 schema 或 policy contract 必须拒绝运行，不得猜测缺失字段或静默使用旧默认值。

## 10. 多样机复用设计方向

`we11` 是当前样机代号，不是框架名、固定产品名或公共控制类型。WE11 专用数据可以存在于 `robots/we11/`、WE11 profile 和 WE11 回归测试中，但公共入口、导出协议、Sim2Sim 主循环、路径解析和 manifest schema 必须使用动态 `robot_id`。

以下写法应逐步消除：

```python
if task_name in {"DR002JoystickFlatWE11", "DR002JoystickGetupWE11"}:
    ...
```

```cpp
if (input_dim != 145 || output_dim != 6) {
    ...
}
```

目标写法由配置和 manifest 驱动：

```text
robot_id        = manifest.robot.id
input_shape     = manifest.policy.input.shape
output_shape    = manifest.policy.output.shape
joint_order     = manifest.robot.joint_order
capabilities    = manifest.robot.capabilities
```

发布目录、基线目录和命令同样参数化：

```text
releases/<robot_id>/<run_id>/
baselines/<robot_id>/<baseline_id>/
python scripts/train.py robot=<robot_id> task=<task_id> algorithm=<algorithm_id> policy=<policy_id>
sim2sim --bundle releases/<robot_id>/<run_id>
```

多样机复用不能只抽象机械模型。框架计划定义五类相互独立、可组合的合同：

| 合同 | 负责内容 | 示例差异 |
| --- | --- | --- |
| `RobotSpec` | 机械资产、关节、actuator、限位、控制频率和能力 | WE11 轮足/机翼与 PE01 点足结构不同 |
| `TaskSpec` | command、reset、termination、reward、curriculum、domain randomization | Getup 与 locomotion flat 使用不同奖励和重置 |
| `ObservationSpec` | actor/critic observation groups、history、scale、noise 和 privilege observation | WE11 当前 145D 合同与 PE01 前身的 30D + 10 帧 history/critic observation 不同 |
| `PolicySpec` | actor/critic/encoder/RNN/adaptation 网络结构、激活函数和导出签名 | PE01 前身包含独立 MLP encoder，不要求套用 WE11 网络 |
| `AlgorithmSpec` | PPO/APPO/SAC 等优化器、runner、storage、loss 和训练超参数 | 新样机可以选择不同训练算法和 runner |

公共层另外提供 `SimulatorSpec` 和 algorithm adapter。环境对训练器暴露稳定的字典 observation groups、action space、reward/done/info 和 checkpointable state；不同 algorithm adapter 决定如何消费这些组，不要求所有算法共享相同 tensor 布局或网络。

`RobotSpec`/robot profile 至少描述：

- robot/asset 标识和路径；
- joint、actuator 和 policy action 顺序；
- 默认姿态和关节限位；
- nominal Kp/Kd；
- action scale 与 clip；
- wheel/leg/wing 等 actuator 分组；
- physics、motor、policy 频率；
- observation schema；
- base、foot、wheel、push site 等语义实体；
- 可选能力，如 wheel、wing、Getup、外力回放；
- export/deployment metadata。

公共环境不得依赖 `"we11"` 字符串判断通用行为。确属 WE11 独有的行为通过明确 capability 或 WE11 extension 实现，例如 `wheeled_legs`、`wings`、`getup_pose_bank` 和 `measured_wrench_replay`。新样机及新算法应当可以通过增加 profile/adapter 注册，而不修改公共 CLI 的枚举或条件分支。

reward 属于 TaskSpec，不属于 RobotSpec；observation 和 policy network 通过显式合同连接；algorithm 只依赖标准环境/rollout 接口。这样 PE01 可以保留自己的 observation history、critic observation、encoder 和奖励设计，同时与 WE11 共用启动、日志、checkpoint、Play、导出和 Sim2Sim 基础设施。

首轮通用化完成的判断标准不是目录重命名，而是第二台样机能够在不修改公共训练入口的情况下完成最小 compose/reset/step。

Deploy 的实际开发、运行和最终验证仍在板端进行；`Aar_Unilab` 不成为 Deploy 的主开发仓库，也不从电脑训练侧直接控制板端。但为了方便对比训练、Sim2Sim 与真机运行链路，新仓库同时保留两套 Deploy 的源码参考快照：

- `host_only`：纯上位机 Deploy 参考；

参考快照主要保留：

- `src/`、`config/`、`scripts/`、`docs/`、`experiments/`；

- `build/`、`install/`、`log/`、`logs/`；

这两套目录是可更新的参考快照，而不是运行依赖：

- Train、Python Play 和 C++ Sim2Sim 不得 import、link 或通过相对路径读取其中代码；

### 11.4 Conda 环境与缓存位置

当前 `/data/miniconda3` 只作为旧环境保留，不作为 `Aar_Unilab` 新环境的依赖。先在 SSD 安装独立 Miniforge：

```text

```

新安装脚本始终使用这个明确的 Conda executable/base，并采用显式 prefix 模式，例如：

```bash
bash tools/install_environment.sh \
  --conda-base /ssd/conda/miniforge3 \
  --prefix /ssd/conda/envs/aar_unilab \
  --torch cu128

source /ssd/conda/miniforge3/etc/profile.d/conda.sh
conda activate /ssd/conda/envs/aar_unilab
```

脚本应使用任务专用变量设置 SSD cache，而不永久修改用户的全局 Conda 配置：

```text
CONDA_PKGS_DIRS=/ssd/conda/pkgs
PIP_CACHE_DIR=/ssd/conda/cache/pip
AAR_UNILAB_NATIVE_BUILD_CACHE=/ssd/conda/cache/aar_unilab-native
```

要求：

- 环境目录与仓库目录分离，移动/删除源码不会删除环境；
- 安装脚本同时支持本机推荐 prefix 和用户自定义 prefix；
- 安装脚本校验实际 `conda info --base` 位于指定 SSD base；
- 所有 `conda run/install/create` 操作使用同一个 resolved prefix；
- 不依赖环境名称解析，避免误用其他盘上的同名环境；
- 安装完成后记录 prefix 和依赖版本，但提交的配置不保存本机绝对 prefix；
- C++ Sim2Sim 的 build/cache 同样默认放在 SSD 的可配置目录。

### 11.5 仓库移动与路径重绑定

Python 源码路径以 `__file__`、package resources 或显式仓库根解析，不以启动时 `cwd`、父目录或固定 `/ssd/Pheonix` 路径解析。manifest 中保存 bundle 内相对路径；本机绝对路径只能作为可选诊断信息，不能参与运行。

开发期间通常执行 editable install。editable install 和 native extension 可能记录源码绝对路径，因此从：

```text
/ssd/Pheonix/Aar_Unilab
```

移动到：

```text
/ssd/Aar_Unilab
```

后必须执行统一重绑定流程，例如：

```bash
source /ssd/conda/miniforge3/etc/profile.d/conda.sh
conda activate /ssd/conda/envs/aar_unilab
cd /ssd/Aar_Unilab
bash tools/rebind_environment.sh --prefix /ssd/conda/envs/aar_unilab
bash tools/validate_installation.sh --all
```

`rebind_environment.sh` 负责重新安装 editable package、重建本地 native extension、清除只与旧源码路径相关的构建缓存；不得删除训练日志、checkpoint 或 Conda environment。

路径可迁移性验收分两次进行：

1. 在 `/ssd/Pheonix/Aar_Unilab` 完成首轮安装和测试；
2. 移动到最终 `/ssd/Aar_Unilab`，执行重绑定并重复完整测试；
3. 额外从仓库创建一个临时普通 clone，确认没有未声明的父目录依赖。

实际 `.gitignore` 应结合文件布局细化，不能为了省事忽略整个 `data/`、`models/`、`assets/`、`references/` 或 `sim2sim/`，以免隐藏正式资产、manifest、测试数据和源码。正式选定的 checkpoint/模型是否进入 Git，按单独的数据治理决策执行；若使用 Git LFS，需要在 `.gitattributes` 中明确类型和安装要求。

Git 质量要求：

- 每次迁移前后查看 `git status --short`，不混入无关生成物；
- 用 `git check-ignore -v <path>` 验证关键 ignore 规则；
- 安装、build、测试、短训练、Python Play 和 C++ Sim2Sim 后，工作区保持干净；
- 增加大文件检查，阻止误提交日志、虚拟环境、runtime 和中间 checkpoint；
- Deploy 参考快照复制时排除嵌套 `.git`，来源 commit 记录在 README/manifest；
- 关键阶段建立可追溯 tag，不重写已经作为 baseline 或 release 发布的历史；
- 在独立 clone 中重复安装和测试，验证提交内容足以恢复项目。

## 12. 产物与数据治理

训练数据、run、checkpoint、正式模型和 release 按“样机 → 任务/环境 → run/version”组织，不使用全局 WE11 专用固定路径。建议目录约定：

```text
data/<robot_id>/<dataset_id>/
logs/<algorithm>/<robot_id>/<task_id>/<run_id>/
checkpoints/<robot_id>/<task_id>/<run_id>/
models/<robot_id>/<task_id>/<release_id>/
releases/<robot_id>/<task_id>/<run_id>/
baselines/<robot_id>/<baseline_id>/
```

例如当前 WE11 和后续 PE01 分别自然落在 `we11/`、`pe01/` 命名空间中。同一 robot 下的 Flat、Rough、Getup 或后续新环境继续按 `task_id` 分开，禁止不同样机或环境共用一个含义模糊的 `latest` 文件。

目录位置参考当前仓库使用方式：开发产生的日志和 checkpoint 可以保存在仓库工作目录下便于查看，但默认加入 `.gitignore`；正式选择的模型、基线 manifest、校验值和必要小型数据进入受控版本目录。每个 run 必须记录 robot、task、Git、resolved config 和 checkpoint provenance。

源码仓库默认不提交：

- `.venv/`；
- `logs/`、TensorBoard event；
- `outputs/`；
- `build/`、`install/`、ROS log；
- Python/test/lint cache；
- 临时 XML、core、视频和调试 CSV；
- 大量中间 checkpoint；
- 可由脚本重新生成的转换产物。

源码仓库可以保留：

- 少量正式发布 checkpoint；
- 对应 SHA-256 和 provenance；
- 小型 golden test data；
- 无法重新生成或具有实验价值的原始实测数据；
- 数据 manifest 和生成脚本。

大日志、完整 checkpoint 序列和硬件采集数据可以先按上述样机/环境目录保存在 SSD；是否进一步迁移到源码仓库外的 artifact 存储不阻塞第一阶段。无论物理存放在哪里，都必须有明确的 robot/task/run 归属和 manifest。迁移前先建立保留清单，不直接删除。

## 17. 已确认的结论

当前讨论已经确认：

1. **基线来源**：以当前本地 UniLab 有效状态为准，历史版本仅作参考。
2. **仓库名称与位置**：新仓库命名为 `Aar_Unilab`，初始位置为 `/ssd/Pheonix/Aar_Unilab`。
3. **物理独立性**：新仓库可以显示在当前 VS Code 工作区，但不得依赖任何父目录或相邻工作区内容。
4. **仓库边界**：Python Train、Python Play 和 C++ Sim2Sim 同仓；真机 Deploy 暂时独立。
5. **C++ 定位**：保留 C++ 回放和跨语言 Sim2Sim 能力，通过生成的 release bundle 降低维护成本。
6. **行为边界**：第一阶段不得改变 WE11 训练配置和环境语义。
7. **历史样机**：不直接找回旧样机代码，只将历史实现作为新样机接入和通用化设计参考。
8. **迁移顺序**：先冻结基线，再建立独立 clone 和 Python Play，再迁移 C++ Sim2Sim，最后进行通用化和清理。
9. **环境位置**：Aar_Unilab 使用安装在 `/ssd` 的独立 Conda/Miniforge；Conda base、environment 和各类安装/build cache 都不再依赖 `/data/miniconda3` 或空间紧张的默认用户目录。
10. **最终仓库位置**：开发验证后仓库将移动到 `/ssd/Aar_Unilab`；代码、配置和 manifest 必须对仓库位置无感。
11. **样机标识**：`we11` 只是一个 robot ID；公共训练、Play、导出和 Sim2Sim 逻辑必须支持动态样机代号，不得写死 WE11。
12. **第二台样机**：复用性验证样机代号为 `pe01`；`DRAGON_3` 是 PE01 实机最终机械资产并作为正式验证基线，其训练代码作为差异化算法、观测、网络和奖励参考。
13. **交互能力**：Python Play 与 C++ Sim2Sim 保留实时渲染、拖动施力、手柄控制、图表绘制和摄像机操作，当前 C++ Play 作为迁移参考。
14. **数据组织**：数据、日志、checkpoint、模型和 release 按 `<robot_id>/<task_id>/<run_id-or-version>` 分层存放，WE11 与 PE01 相互隔离。
15. **MuJoCo 版本**：以当前 WE11 Python 训练实际使用的 3.8.0 为统一基线，C++ 从 3.2.7 升级对齐，并保留迁移差异验证。
16. **多训练栈**：新样机不要求采用 WE11 的算法、observation、policy network 或 reward；框架通过 Robot/Task/Observation/Policy/Algorithm 五类合同和 adapter 支持组合差异。
17. **Sim2Sim 算法无关**：C++ 只消费导出后的 policy contract，不复刻 PPO、critic、reward 或训练 runner；encoder/RNN/多输入等推理结构由 PolicySpec 显式描述。
18. **Deploy 参考快照**：纯上位机和上下位机两套 Deploy 源码都复制进 `references/deploy/` 供对比与 debug；实际 Deploy 开发仍在板端，参考代码不成为训练侧运行依赖。
19. **Git 管理**：`Aar_Unilab` 从创建开始使用普通 Git；先提交仓库骨架和 `.gitignore`，后续按可验证阶段提交并为 WE11 baseline 等关键节点打 tag。
20. **忽略规则**：环境、缓存、日志、build 和中间 checkpoint 必须被忽略；正式机器人资产、配置、manifest、合同测试和 Deploy 源码参考不得被宽泛规则意外忽略。
